# ADR: SlotMind architecture decisions

Format (the brief's): **Context -> Options -> Decision -> Tradeoffs**. Each entry names the requirement or failure mode it answers. Status "Accepted (design)" means decided at design time and to be re-checked against the code at the end of the build. Related: [PROBLEM.md](PROBLEM.md), [DESIGN.md](DESIGN.md), [AI_LAYER.md](AI_LAYER.md).

## ADR-001: Database and persistence (H2 default, Postgres for the demo, JPA)
**Answers:** T-1 domain model, I1 no double-booking, repeatable tests.
**Context:** The starter ships H2 and PostgreSQL drivers, a Postgres profile on port 5433 and Docker Compose. Tests must run with no external service. Concurrency guarantees must hold on both databases.
**Options:** (a) H2 only; (b) Postgres only; (c) H2 for tests and default run, Postgres for the demo; plus schema from Flyway vs from Hibernate.
**Decision:** (c). JPA/Hibernate with constraints declared on the entities (`@Table` unique constraints, indexes, `@Version`). String ids as in the brief's seed. Schema generated by Hibernate (`ddl-auto`), no Flyway. Seed loaded by a Java `ApplicationRunner` because `NOW() + 60` is not portable SQL. No database-specific SQL, no partial indexes, so both databases behave the same.
**Tradeoffs:** Hibernate-generated schema is not migration-safe for production (Flyway would be added at the first real deployment). H2 and Postgres isolation differ slightly, so the concurrency guarantees rely on `@Version` and UNIQUE constraints (portable) rather than on isolation levels. The thread test runs on H2; the Postgres run is checked once manually.

## ADR-002: Where scheduling logic lives, and how conflicts are prevented (brief ADR Q1)
**Answers:** T-1, T-2, I1, I8.
**Context:** Booking rules, state transitions and recommendation logic could sit in controllers, services or entities. Conflicts must be impossible at the domain boundary, not just unlikely.
**Options:** (a) all rules in services over anemic entities; (b) rich domain entities plus services for orchestration; (c) a separate domain-service layer.
**Decision:** (b), minimal. Entities own state changes (`Slot.book()`, `release()`, `cancel()`, `Appointment.markPending()`, `reschedule()`, `Suggestion.accept()`), throw on illegal moves, and expose no status setters. Services own transactions, loading and event publishing. The recommendation logic lives in `scheduling` as pure functions of an immutable request (no JPA), so it is unit-testable without a database. Conflicts are stopped by the database: `@Version` on every contended row plus a UNIQUE `appointments.slot_id` (see ADR-004).
**Tradeoffs:** Entities carry some logic, which is a little more code than anemic entities. The pure `scheduling` package needs a snapshot-building step in the service (one extra record mapping). In exchange the LLM call can never run inside a transaction (I5).

## ADR-003: Runtime strategy switching (brief ADR Q2)
**Answers:** T-2 pluggable engine, "switchable via config", "HTTP and async share one contract".
**Context:** Rule-based and AI strategies must be selectable at runtime, from both `POST /suggest` and the async loop, and a third strategy must be addable in sprint 2.
**Options:** (a) `if/else` on a flag; (b) a factory class; (c) Spring collects all `SchedulingStrategy` beans into a registry keyed by `name()`; (d) a bean-per-profile.
**Decision:** (c). `StrategyRegistry` receives `List<SchedulingStrategy>`, builds a map, and `active()` reads `slotmind.scheduling.strategy`. `POST /appointments/{id}/suggest?strategy=` overrides per call through the same registry. Both callers use `RescheduleService.plan`, so there is one code path. `AiStrategy` holds the `RuleBasedStrategy` as its fallback.
**Tradeoffs:** A property change needs a restart; the per-call query parameter gives demo-time switching without a restart. No admin endpoint to flip the default at runtime was built (not asked for). A strategy needing extra data (rooms) must add fields to `SchedulingRequest` (additive record change), so adding a strategy is "one class" only while its data is already in the request (see ADR-010).

## ADR-004: Transactional accept and the double-booking race (brief ADR Q3, AGT-3)
**Answers:** T-1 "no double-booking", I1, I2, I3.
**Context:** Two staff can accept different suggestions that point at the same slot (the seed itself produces this: APT-001 and APT-002 both get SLT-005), or click accept twice.
**Options:** (a) pessimistic row locks (`SELECT ... FOR UPDATE`); (b) optimistic `@Version`; (c) serializable isolation; (d) a UNIQUE constraint alone.
**Decision:** Layered defence in one `@Transactional` accept method: (1) re-validate state (suggestion PENDING, appointment RESCHEDULE_PENDING, slot OPEN, target provider not OFFLINE); (2) `@Version` on slot, appointment and suggestion, so of two concurrent writers one flush fails; (3) UNIQUE `appointments.slot_id` as a backstop that no code path can bypass. `ObjectOptimisticLockingFailureException` and `DataIntegrityViolationException` map to `409 CONCURRENT_UPDATE`. Suggestions do not reserve slots (ADR-006).
**Tradeoffs:** The loser gets a 409 and must retry or pick another suggestion instead of waiting for a lock. Pessimistic locking would serialise accepts and avoid the 409, but needs lock-timeout handling and behaves differently on H2 and Postgres. Proven by a thread test (ExecutorService + CountDownLatch): exactly one 200, the rest 409.

## ADR-005: Agentic loop decoupling (brief ADR Q4, AGT-1)
**Answers:** T-4, I5, I6.
**Context:** Provider-offline affects many appointments; slot-cancelled affects at most one. Endpoints must return immediately and no LLM call may sit in a DB transaction.
**Options:** (a) two event types and two handlers; (b) one event type and one handler branching on a trigger field; (c) a message broker; (d) a scheduled poller.
**Decision:** (b). `ProviderService` and `SlotService` change state and mark the affected `CONFIRMED` appointments `RESCHEDULE_PENDING` in one transaction, then publish `RescheduleRequested(trigger, appointmentIds)`. A `@TransactionalEventListener(AFTER_COMMIT)` + `@Async("rescheduleExecutor")` handler processes each id (try/catch per id) through `RescheduleService.plan`, which is: read-only snapshot tx -> strategy (no tx) -> short write tx. The trigger only selects the prompt. Executor is bounded (core 2, max 4, queue 200, abort policy).
**Tradeoffs:** Events are in-memory: a crash between commit and handler loses the work, and the appointment stays `RESCHEDULE_PENDING` without a suggestion (visible in the UI, recoverable via `POST /suggest`). A durable outbox or broker would fix that at much higher cost (see Not built). Sequential processing per event keeps load on the LLM predictable but is slower for large batches.

## ADR-006: Suggestions do not reserve slots
**Answers:** I3, T-4 human checkpoint.
**Context:** A suggestion is a proposal that a human confirms with the patient, possibly minutes later.
**Options:** (a) hold the slot (status `HELD`) until decided; (b) no hold, validate at accept.
**Decision:** (b). No hold state exists; accept re-validates (ADR-004). Rejected slots are excluded from later suggestions for the same appointment.
**Tradeoffs:** The second of two suggestions for one slot fails at accept time (409) rather than being avoided up front. A hold would avoid that but needs expiry timers, a cleanup job and more states, and could starve slots if staff forget to decide. Accepted as a deliberate, demonstrable behaviour.

## ADR-007: At most one PENDING suggestion per appointment and trigger
**Answers:** T-4 "skip duplicate PENDING", I6.
**Context:** Repeated PATCHes or concurrent triggers must not create duplicates. H2 has no partial unique indexes.
**Options:** (a) check-then-insert in code (racy); (b) partial unique index (not portable); (c) nullable UNIQUE `pending_key` = `appointmentId:trigger` while PENDING, NULL once decided.
**Decision:** (c). A duplicate insert violates the constraint and is skipped. The service also checks first to avoid noisy exceptions.
**Tradeoffs:** One denormalised column maintained by the entity's `accept()`/`reject()`. Manual `/suggest` additionally returns 409 if any PENDING suggestion exists.

## ADR-008: AI is advisory, validated and always has a fallback
**Answers:** T-3, I4, I7, I10.
**Context:** The model can invent ids, pick unavailable slots, refuse, time out or return malformed JSON. Details in AI_LAYER.md.
**Options:** (a) trust the model output; (b) constrain with structured outputs only; (c) closed candidate set + strict parsing + membership validation + deterministic fallback + human accept.
**Decision:** (c). The model chooses only among slot ids we send; any validation failure uses `RuleBasedStrategy` and records `fallbackCause`; the model never writes data. Official `anthropic-java` SDK behind our `LlmClient` interface. `temperature` is not sent because current Claude models reject it; thinking stays on with effort `LOW`. Model is configurable, default `claude-opus-5-5` (Haiku 5.5 is the cheaper option to evaluate). Two prompts by trigger.
**Tradeoffs:** Output is not bit-for-bit deterministic; the validator and fallback absorb that. Opus-class latency at low effort may approach the 8 s timeout, in which case the fallback answers. Server-side `fallbacks` on refusal was not used; our own rules fallback covers it.

## ADR-009: Polling for the UI queue, SSE only as the bonus
**Answers:** T-5 "polling, loading, error states", cut order.
**Context:** The front-desk queue changes on human-scale events at one clinic.
**Options:** (a) polling; (b) SSE for queue updates; (c) WebSockets.
**Decision:** (a) every 4 s on `GET /appointments?status=RESCHEDULE_PENDING`. SSE appears only in the optional `/suggest/stream` bonus.
**Tradeoffs:** Up to 4 s latency and steady idle requests. At 100x load: first make polls cheap (ETag/`since` cursor, cached counts); then move to SSE on virtual threads with Redis pub/sub for multi-instance fan-out. Polling is stateless and scales horizontally; SSE holds a connection per viewer, which under Tomcat's thread-per-request model is the first resource to run out.

## ADR-010: Extensibility and exclusions (brief ADR Q5)
**Answers:** T-2 "RoomConstraintStrategy = implement and register", sprint 2/3 roadmap.
**Context:** Sprint 2 adds room/equipment constraints, duration by type, patient preferences; sprint 3 adds waitlist, notifications, multi-clinic.
**Decision:** The seams are `SchedulingStrategy` (new class, registered by `@Component`) and `LlmClient`. Constraint data is added as new record components on `SchedulingRequest` (built in `RescheduleService`), so existing strategies are untouched. Waitlist auto-fill would be another consumer of a "slot opened" event published next to `RescheduleRequested`; notifications a listener on accepted suggestions. Deliberately deferred: everything in the list below.
**Tradeoffs:** Not literally zero changes for a strategy that needs new data (the snapshot builder and request record change). Kept honest here rather than hiding it behind a generic context map.

## Practices applied, and what each answers
| Practice | Requirement / failure mode |
|---|---|
| Layering controller -> service -> repository, constructor injection | maintainability; ADR-002 |
| DTO records, entities never returned | API stability; lazy-loading errors |
| Bean Validation + one `@RestControllerAdvice` + one error body | T-1 400s; consistent client handling |
| Entity methods guard state transitions, no status setters | I8; illegal lifecycle moves |
| `@Version` on Provider, Slot, Appointment, Suggestion | I1/I2 lost updates; concurrent status flips |
| UNIQUE `slot_id`, UNIQUE `pending_key`, FKs, CHECKs, indexes | I1, I6; query plans for filters/joins |
| Enums stored as STRING | schema stability when enums are reordered |
| AFTER_COMMIT event + bounded `@Async` executor | I5 no LLM in a transaction; T-4 non-blocking endpoints |
| Timeouts, `maxRetries(0)`, fallback on every LLM call | T-3, I7 |
| Secrets only from `LLM_API_KEY`, startup warning, `.env` ignored | I10 |
| Unit tests for rules and failure paths + IT per endpoint | rubric T-1..T-4 evidence |
| Thread-based test (ExecutorService + CountDownLatch) | **trigger:** AGT-3 "two staff, one slot" |
| Pagination (default 20, max 50) on `GET /appointments`, `GET /slots` | **trigger:** lists that grow |
| Idempotency key | **not triggered:** a retried `POST /appointments` hits `SLOT_NOT_OPEN` 409 (natural idempotency); accept replays hit `SUGGESTION_NOT_PENDING` |
| Rate limiting, caching | **not triggered:** the brief names no load or read-heavy requirement |

## Not built, and what I would add
| Not built | Add it when |
|---|---|
| Durable outbox / message broker for the reschedule event | the process crashing between commit and handler becomes unacceptable, or work must survive restarts (add a transactional outbox table first, a broker only at multi-service scale) |
| Slot holds with expiry for suggestions | staff routinely collide on accepts (many simultaneous coordinators) |
| Re-planning a `RESCHEDULED` appointment whose new provider goes offline (the brief re-plans `CONFIRMED` only) | immediately in sprint 2; it is one extra allowed transition and status in the loop query |
| Auto-marking losing suggestions stale after a 409 | usability feedback shows staff confused by stale cards |
| SSE/WebSocket push for the queue | roughly hundreds of concurrent viewers or sub-second latency needs (ADR-009) |
| Caching, rate limiting, ETag polling | read load or abuse appears; ETag first |
| Idempotency keys on writes | clients that auto-retry non-idempotent calls appear |
| Authentication and roles | any non-demo deployment |
| Flyway migrations | first deployment with data worth keeping |
| Room/equipment constraints, patient preferences, waitlist, notifications, multi-clinic, portal | sprints 2 and 3 of the roadmap |
| Spring AI, Lombok, mapping libraries, generic base classes | never needed at this size |
| Multi-instance deployment | needs shared event delivery (see outbox) and a shared executor/queue |
